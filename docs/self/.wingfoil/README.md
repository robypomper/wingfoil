# `.wingfoil/` — WingFoil's own configuration (dogfooding)

This directory is the **WingFoil configuration for the WingFoil project itself**. The Product Brief
commits WingFoil to being its own first production user — *"WingFoil development is managed by
WingFoil"*. This is that configuration.

## Why it lives here and is hand-authored

The `wingfoil` CLI/MCP tooling is **not yet implemented**, so `wingfoil init` cannot generate this
config. Every file here was written **manually**, following the specifications in:

- `docs/01_vision/` — vision, personas, journeys, features, CLI commands, Lean Inception plan
- `docs/02_requirements/` — user story map, BDD suite, SARD (Volere), and the downcast plan

It is placed under `docs/self/.wingfoil/` (rather than the repo root) precisely because the tool
does not exist yet. **Once the `wingfoil` CLI is implemented, this directory should move to the
repository root `.wingfoil/`** so the tool can manage it for real.

## Layout

| Path                           | Pillar                 | Purpose                                                        |
|--------------------------------|------------------------|----------------------------------------------------------------|
| `dna.yaml`                     | DNA (P2.4)             | Modules, stacks (technologies + methodologies), team + roles, resource paths |
| `memory.yaml`                  | Memory (P1.13)         | Element types, per-type state machines, and `template:` scaffolds with `frontmatter.required` (P4.12 alignment rule in file header) |
| `memory/`                      | Memory (P1.11)         | Element-type `templates/` (below); element **content** lives at `docs/04_memory/` (under `docs/self/`) |
| `memory/templates/`            | Memory (P1.13)         | One Markdown scaffold per element type — generated by `wingfoil memory add`; `frontmatter.required` aligns with P4.12 workflow checks |
| `directives/built-in/`         | Directives (P3.8)      | Empty for now — official P3.8 templates not yet implemented (see note below) |
| `directives/custom/`           | Directives (P3.5/P3.8) | WingFoil rules + P3.8 template **stand-ins** (`kind: custom`, `ref: [P3.8]`)  |
| `roles.yaml`                   | Directives (P3.2/P3.7) | Role → directive bindings                                      |
| `workflows.yaml`               | Workflow (P4.1)        | Main config; `include()`s the workflow files                   |
| `workflows/custom/`            | Workflow (P4.1)        | 4 `main` (`sw-life-cycle` + 3 ingest) + the `sub` workflows they compose |

> **Directives — built-in vs custom (interim decision):** WingFoil's official built-in directive
> templates (P3.8) don't exist yet, and generic built-ins are hard to pin down (they depend on each
> project's methodology/tech-stack — see `dna.yaml`). So the six P3.8 templates (code-quality, testing,
> code-review, architecture, security, documentation) are kept in `directives/custom/` as **stand-ins**
> — each `kind: custom` with `ref: [P3.8]` — and move to `directives/built-in/` once the official
> templates are implemented.

> **Memory paths:** `memory.yaml` declares each type's `path` under `docs/04_memory/` (e.g.
> `docs/04_memory/planning/{id}.md` for `release-line`, `docs/04_memory/planning/{release-line}/{id}.md`
> for `release` — nested under its parent release-line's version). For this dogfooding setup those
> resolve against the `docs/self/` root, so the files live at `docs/self/docs/04_memory/...` —
> **matching** the declared paths. Once the tool manages the config from the repository root
> `.wingfoil/`, the same paths resolve to `docs/04_memory/` directly. Release content is derived from
> `docs/03_backlog/` (each release's `requirements:` points to its by-release backlog JSON).

## Workflow model

The primary startable **main** workflow, `sw-life-cycle`, composes the lifecycle as include-only
**sub** workflows; three small **ingest mains** capture single Memory elements on demand. Multiple
open mains are allowed (REQ-STATE-03 / REQ-SYS-06):

```
sw-life-cycle (main)
├── inception        → lean-inception                 [DONE]
├── specification    → specification-downcast          [DONE]
│                       ├── user-story-mapping          (USM, Module 1)
│                       ├── specification-by-examples   (BDD, Module 2)
│                       ├── volere-requirements         (SARD, Module 3)
│                       └── backlog-export              (Module 4)
├── init                    → wingfoil-init         (config pillars only)
├── seed-first-release-line → memory.add(release-line v1)  (inline phase, no include)
├── release-line-cycle      → release-line-cycle    (iterate_over: release-line)
│                              ├── approve            (release-line: planning → active)
│                              ├── initial-design      (seed-releases + optional ADRs/DLs/tech-specs,
│                              │                        scoped to this release-line — reusable per major version)
│                              ├── delivery            → release-cycle  (iterate_over: release,
│                              │                        scoped where release-line = this one)
│                              │     ├── release-planning  (identify-specs; optional: record ADRs)
│                              │     ├── dev-loop  (design gate + TDD, iterate_over: task; gate runs BDD;
│                              │     │              fix tasks keep their source bug in sync via bug.sync_state)
│                              │     ├── release-submit
│                              │     ├── release-publishing
│                              │     └── retrospective  (→ decision-log)
│                              └── plan-next-release-line  (once all releases are `released`:
│                                                            close this release-line, self-seed the next)
└── sunset                  → end-of-life            (→ decision-log)

Ingest mains (startable on demand, REQ-STATE-03):
  bug-ingest           → capture a bug
  decision-log-ingest  → capture a decision-log
  adr-ingest           → capture an ADR  (used during dev-loop / other phases)
```

`lean-inception` and `specification-downcast` are marked **done** and modeled from their existing
plan files (`docs/01_vision/X_lean-inception-plan.md`,
`docs/02_requirements/X_specs-downcast-plan.md`). The delivery and sunset workflows follow best
practice adapted to WingFoil's weekly, per-pillar release cadence.

## Conventions honored

- **No `.wingfoil/state/` index** — state is deduced from Memory frontmatter (REQ-SYS-03).
- **Multiple `kind: main` allowed** (REQ-STATE-03) — `sw-life-cycle` + the three ingest mains; every non-main is `kind: sub`.
- **Role-based binding** — directives/approvals bind to roles in `dna.yaml`, never to people (REQ-SYS-08).
- **Legal states only** — every `memory/*/*.md` `status:` is valid for its type per `memory.yaml`.
- **Traceability** — releases link to features via frontmatter `features:`; tasks will link likewise once produced by workflows.
- **P4.12 alignment** — every workflow step that calls `memory.add` declares `checks.post: ["frontmatter.required: [...]"]`; the field list must match the type's `template.frontmatter.required` in `memory.yaml` (authoritative source). If they diverge, update the workflow check.

## Field-provenance convention (`[SPEC]` / `[AUTHORING]`)

`dna.yaml` and `memory.yaml` annotate every field with one of two provenance tags (visible as inline
comments):

| Tag | Meaning |
|-----|---------|
| `[SPEC]` | The field is **required or explicitly defined** by the specifications. An inline reference (feature ID, REQ code, or BDD scenario) is always cited. |
| `[AUTHORING]` | The field is an **authoring addition**: structurally coherent with the specs but not mandated by them. Added to make the configuration complete, navigable, or useful for agents — without over-specifying. |

This is a **human-audit aid**, not a runtime flag — the WingFoil engine does not distinguish between
the two at load time. Its purpose is to make it immediately clear, during review or future evolution,
which fields can be changed freely and which ones are anchored to a specification that must be updated
first.

**Rules when editing these files:**

- Field backed by a feature, REQ, or BDD scenario → mark `[SPEC]` and cite the reference inline.
- Field added for clarity, navigation, or tooling convenience → mark `[AUTHORING]`.
- Removing or renaming a `[SPEC]` field requires a corresponding change in the referenced specification.

> Scope: sourced from `docs/01_vision/` and `docs/02_requirements/`, plus `docs/03_backlog/` for the
> per-release requirement assignment (release frontmatter `requirements:`). Other `docs/` subdirs
> (`design_`, `simulation`, `specs_`) are intentionally not used here.
