## Context

WingFoil keeps everything it can in the repository. Some of what the project depends on cannot live
there, though: an account on a registry, a credential held by a CI platform, a setting in a hosting
platform's UI, a listing in a third-party directory. On 2026-09-28, while planning the project's public
visibility (`decision-log-ingest-rel-v0.3-visibility-plan`), the approver ruled that such state is
still **recorded in the repository**, as Memory: what it is, how it works, and how to manage it. The
approver also ruled that the record is a **new Memory type**, rather than a tech-spec register or a
section of `dna.yaml`. This DL designs that type.

### The project already has this state, and it is recorded piecemeal

Publishing v0.2 created four pieces of external state that the release pipeline cannot work without:

| External state | Where it is described today |
|---|---|
| The npm package `wingfoil` and the npm account that owns it | `adr-009-npm-publishing-pipeline`, `spec-015-packaging-publishing` |
| The `NPM_TOKEN` Actions secret: its token type, and the January 2027 end of direct publishing | `task-061-publish-secrets`, `dl-087-publish-through-npm-staged-publishing` (`in-discussion`) |
| The GitHub environment `npm-publish` and its required reviewer | `task-061-publish-secrets`, the runbook in the header of `.github/workflows/publish.yml` |
| The repository's public visibility, a precondition of provenance | `dl-068-publishing-requires-public-repository` |

Each of those documents records the fact as a side note of something else: a task, a decision, a
spec. None of them is the authoritative record of the external thing itself.
`grep -rln NPM_TOKEN docs/self/docs/04_memory | wc -l` → `12`, and
`grep -rln npm-publish docs/self/docs/04_memory | wc -l` → `20` (both run on 2026-09-28). So the
question *"what does WingFoil depend on outside git, who manages it, how do I check it, and when does it
expire?"* can only be answered by reading all of them. This is the same symptom `dl-019` found for
phase plans before `plan` became a type: state that drives real work, with no frontmatter to query.

The visibility work is about to add many more such pieces: a domain, reserved handles, an npm scope,
MCP registry and directory listings, repository settings, Pages, Discussions. Without a type, each one
would become another side note.

### Why `dna.yaml` does not already cover it

`dna.yaml` `stacks.technologies` lists `npm registry (public)` with `category: distribution`. That
entry is a **technology choice**: the project distributes through npm. It does not describe the
**operated instance** — which account, which token, which settings, and what to do when the token
expires. Keeping the two apart matches how `dna.yaml` already treats `git` (a technology) and the
repository on GitHub (not described anywhere).

## Decision

Add a Memory type **`service`** (`[AUTHORING]`, with this DL as its provenance, and `P1.13` as the
feature that lets `memory.yaml` declare types).

A `service` element records **one unit of state that lives outside the git repository and that the
project owns, depends on, or presents itself through**. That covers an account or identity, a
credential (by reference only), a listing in a registry or directory, a settings block on a hosting
platform, a domain, or a reserved handle.

The type does **not** cover:

- technology choices, which stay in `dna.yaml`;
- third-party libraries, which stay in `package.json`;
- intentions, which are decision-logs and tasks. A `service` element describes something that has been
  set up, not something the project plans to set up.

### Proposed `memory.yaml` entry

```yaml
service:
  path: "docs/04_memory/services/{id}.md"
  id_pattern: "svc-{n}-{slug}"            # e.g. svc-001-npm-package-wingfoil
  name: External Service
  description: >-
    One unit of state outside the git repository that the project owns, depends on, or presents
    itself through (account, credential by reference, registry/directory listing, platform setting,
    domain, handle). Workflow — created on demand via the `service-ingest` main, and by any phase
    that sets up external state (e.g. release-publishing). See dl-088.
  tags: [ service, external, operations ]
  template:
    frontmatter:
      required: [ title, provider, kind, owner_role, verify ]
    file: ".wingfoil/memory/templates/service.md"
  states:
    sequence: [ draft, pending, active ]
    gates:
      pending: { reject: draft }          # approve: pending->active · reject: ->draft
    waiting: [ ]                          # `active` is terminal; retirement is memory.deprecate
```

The states mean:

- **`draft`** — the element is registered (`memory.add`).
- **`pending`** — the external state exists and is configured as the body describes. It is filled in
  and submitted (`memory.submit`) by whoever set it up.
- **`active`** — the approver has run the element's `verify` and confirmed that the description holds
  (`memory.approve`). The approval gate is a human verification of the outside world, which no agent
  can perform without credentials it must not hold.
- **retirement** — `memory.deprecate`, the reserved wildcard, from any state. The `Reason:` says why
  the service was dropped or what replaced it.

### Frontmatter

| Field | Required | Content |
|---|---|---|
| `title` | yes | e.g. "npm package `wingfoil`" |
| `provider` | yes | who hosts it: `npmjs.com`, `GitHub`, `registry.modelcontextprotocol.io`, … |
| `kind` | yes | one of `account`, `credential`, `listing`, `setting`, `domain`, `handle` |
| `owner_role` | yes | the `dna.yaml` role that manages it — a role, never a person (REQ-SYS-08) |
| `verify` | yes | the command or URL that establishes its current state (`claim-evidence`) |
| `url` | no | its public URL, if it has one |
| `account` | no | the public identifier used (e.g. `robypomper`); never a secret |
| `renews` | no | ISO date on which it expires or must be renewed; `""` if never |
| `repo_refs` | no | repository paths that depend on it (e.g. `.github/workflows/publish.yml`) |
| `decision` | no | the DL or ADR that motivated it |
| `release` | no | the release in which it was set up |

### Body

The body has four sections:

- **Purpose** — why the project needs it.
- **Configuration** — how it is set up and which of its settings matter.
- **Verification** — the `verify` procedure and the expected result.
- **Management** — renew, rotate, recover and retire procedures, with deadlines.

### Security rule

A `service` element **never contains a secret value**: no token, password or recovery code, and no
fragment of one. It names where the secret is held (e.g. "GitHub Actions secret `NPM_TOKEN`, repository
scope"), its type, its expiry, and how it is rotated. This is REQ-SEC-08 and the `security-secrets`
directive applied to a type whose subject matter makes the mistake likely. The spec-007 scan is a
mandatory `post` check of the `capture` phase, as it is for decision-logs.

### Options still open for the approver

1. **State machine.**
   - *(a)* `draft → pending → active` as above. **Recommended.**
   - *(b)* Add a `planned` state before `pending`, for services decided but not yet set up. Not
     recommended: intent already has a home (a DL, a task, a plan), and a `service` element that
     describes something not yet real would make `active`/`pending` harder to trust.

## Rationale

- **The approver's rule needs a home.** "Everything is in the repository, and what is not is
  recorded in it" is only checkable if the record has a declared shape. A type gives it one:
  frontmatter that can be queried (`grep -r "^renews:"`), a state that can be validated, and an approval
  that means something specific.
- **Why a type and not a register document.** A single tech-spec would be one file with one status for
  everything, so a stale credential could not be marked independently of a healthy listing. Per-element
  state, git history and `deprecate` all come for free with a type.
- **Why not `dna.yaml`.** It would need a `spec-002` change for an `[AUTHORING]` concern, and it would
  mix what the project *is* with what the project *operates*.
- **Determinism.** The next agent, or the next maintainer, that meets an expired token finds its
  rotation procedure by type rather than by archaeology across 12 documents.
- **Dogfooding.** A project that uses WingFoil will have exactly this problem. Solving it here with
  a configurable type is evidence for P1.13's claim that types are the extension point.
